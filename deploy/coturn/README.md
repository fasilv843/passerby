# TURN server (coturn)

Most calls connect directly, peer to peer, using STUN to discover public addresses.
When both people are behind strict NATs (common on mobile data and office networks),
there is no direct path, and media has to be relayed through a TURN server.
Without one, those calls never connect.

## How credentials work

Passerby uses coturn's time-limited credentials (`use-auth-secret`):

1. coturn and the Passerby server share one secret, `TURN_SECRET`.
2. When two users are matched, the server sends each of them
   `username = "<expiry>:<socket id>"` and `credential = base64(HMAC-SHA1(secret, username))`.
3. coturn recomputes the HMAC and rejects the credential after the expiry (`TURN_TTL`, default 1 hour).

The secret never reaches the browser, and no per-user state is stored.

## Run it

On a VM with a public IP, open TCP/UDP 3478, TCP 5349 and UDP 49160–49200, then:

```bash
export TURN_SECRET=$(openssl rand -hex 32)
docker compose -f deploy/docker-compose.coturn.yml up -d
```

If the VM is behind NAT (AWS, GCP, Azure), set `external-ip` in `turnserver.conf`.

Then set these on the Passerby server:

```env
TURN_URLS=turn:turn.example.com:3478?transport=udp,turn:turn.example.com:3478?transport=tcp,turns:turn.example.com:5349?transport=tcp
TURN_SECRET=<same value>
TURN_TTL=3600
```

`turns:` on 5349 needs a TLS certificate (see the commented `cert`/`pkey` lines). It helps on
networks that block everything except HTTPS-like traffic.

## Check that it works

1. Open https://webrtc.github.io/samples/src/content/peerconnection/trickle-ice/
2. Add your `turn:` URL with a username and credential generated by the server
   (log one from `getIceServers()`, or compute it with the formula above).
3. Gather candidates. A `relay` candidate means TURN is working.

In Passerby, the badge on the remote video shows **Relayed · TURN over UDP** when a call goes through coturn.
To force it while testing, set `iceTransportPolicy: "relay"` in `PeerSession`'s `RTCPeerConnection` config.
